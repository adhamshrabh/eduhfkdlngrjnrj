# دليل التشغيل — منصّة الروضة على الخادم

المرجع لمن يشغّل الخادم: كيف يُنشر إصدار، وكيف يُتراجَع عنه، وماذا يُفعل حين
يتعطّل شيء. كل أمرٍ هنا يُشغَّل من **جذر المستودع على الخادم**.

---

## القواعد الخمس

1. **لا نشر إلا بـ `deploy/deploy.sh`.** لا `docker compose up --build` يدوياً:
   السكربت هو ما يأخذ النسخة الاحتياطية ويفحص ويتراجع.
2. **لا نشر إلا من commit نجح عليه CI** (علامة ✓ خضراء على GitHub). السكربت
   يرفض الشجرة المعدَّلة، لكنه لا يعرف إن كانت الاختبارات نجحت.
3. **لا نشر وقت الحصص.** التبديل ثوانٍ، لكن إن احتاج تراجعاً فلتكن الغرفة فارغة.
   الأنسب: بعد الظهر أو المساء.
4. **`DJANGO_DEBUG=1` لا يوضع على الخادم أبداً.** يكشف تفاصيل الأخطاء للزوّار،
   والسكربت يرفض النشر معه.
5. **ما لم يُجرَّب استرجاعه ليس نسخة احتياطية.** تمرين الاستعادة (أدناه) مرّة كل شهر.

---

## أوّل تشغيل على خادمٍ جديد

```bash
git clone https://github.com/adhamshrabh/eduhfkdlngrjnrj.git rawda && cd rawda
cp deploy/env.example .env && chmod 600 .env     # ثم املئي القيم
sudo cp deploy/nginx-rawda.conf /etc/nginx/conf.d/rawda.conf && sudo nginx -t && sudo systemctl reload nginx
deploy/deploy.sh
```

ثم نقل القصص (قاعدة البيانات + مجلد `media`) — انظري «نقل المحتوى» أدناه.

---

## النشر

```bash
git pull
deploy/deploy.sh
```

ما يجري، بالترتيب:

| الخطوة | إن فشلت |
|---|---|
| فحص مسبق: `.env` كامل، لا `DEBUG`، لا تعديلات غير محفوظة، ٥ غيغا حرّة على الأقل | يتوقّف قبل أن يلمس شيئاً |
| نسخة من قاعدة البيانات في `backups/predeploy-<الإصدار>-<التاريخ>.sql.gz` | يتوقّف قبل أن يلمس شيئاً |
| بناء صورة `rawda-backend:<الإصدار>` — **الإصدار القديم ما زال يخدم** | يتوقّف؛ القديم يعمل كما هو |
| التبديل إلى الصورة الجديدة، ثم انتظار `/healthz` | **تراجعٌ تلقائي** إلى الإصدار السابق |
| `deploy/smoke.sh`: التطبيق، الاستوديو، كودهما، قصّة منشورة، الواجهة البرمجية | **تراجعٌ تلقائي** إلى الإصدار السابق |

رقم الإصدار هو وسم git إن وُجد على الـ commit (مثل `v1.2.0`)، وإلا بصمته القصيرة.
لإصدارٍ باسمٍ مقروء:

```bash
git tag v1.2.0 && git push origin v1.2.0      # على جهاز التطوير، بعد نجاح CI
```

## التراجع

```bash
deploy/deploy.sh --rollback            # إلى الإصدار السابق
deploy/deploy.sh --status              # ما يعمل الآن + الإصدارات المحفوظة
deploy/deploy.sh --rollback v1.1.0     # إلى إصدارٍ بعينه (آخر ثلاثة محفوظة)
```

⚠️ التراجع يعيد **الكود** لا **البيانات**. إن كان الإصدار المعطوب أجرى ترحيلاً
غيّر الجداول بما لا يفهمه القديم، فالاستعادة من `backups/predeploy-…` (أدناه).

## الفحص في أي وقت

```bash
deploy/smoke.sh                                   # من الخادم، مباشرةً إلى الحاوية
deploy/smoke.sh https://srv1714868.hstgr.cloud    # من أي مكان، عبر nginx والشهادة
curl -s https://srv1714868.hstgr.cloud/healthz    # للمراقبة الخارجية
```

**مراقبة خارجية (موصى بها):** خدمة مجّانية مثل UptimeRobot تطلب `/healthz` كل
خمس دقائق وتراسلكِ حين لا يعود `200`. هكذا يُعرف العطل قبل أن تتّصل معلّمة.

## السجلّات

```bash
docker compose logs --tail 100 backend      # آخر مئة سطر
docker compose logs -f backend              # متابعة حيّة
docker compose logs backend | grep -E "ERROR|Internal Server Error"
```

كل خطأ 500 يُطبع الآن كاملاً مع تتبّعه (كان يضيع قبل ذلك). والسجلّات تُدوَّر
تلقائياً (٥ × ٢٠ ميغا لكل خدمة) فلا تملأ القرص.

## الاستعادة من نسخة احتياطية

> ⚠️ هذه الأوامر **لم تُجرَّب بعد على الخادم**. أوّل تمرين استعادة هو ما يُثبتها.

**قاعدة البيانات** (نسخة ما قبل النشر، أو اليومية `backups/edu-<ختم>.sql.gz`):

```bash
docker compose stop backend
docker compose exec -T db dropdb -U edu edu
docker compose exec -T db createdb -U edu edu
gunzip -c backups/<الملف>.sql.gz | docker compose exec -T db psql -U edu -d edu -q
deploy/deploy.sh --rollback <الإصدار الذي يوافق النسخة>   # يُقلع الخادم ويفحصه
```

**الصور والأصوات** (`backups/media-<ختم>.tar.gz` — الختم نفسه كختم قاعدة البيانات):

```bash
docker compose run --rm --no-deps -v "$PWD/backups:/backups:ro" --entrypoint sh backend \
  -c "cd /app/media && tar -xzf /backups/media-<ختم>.tar.gz"
```

### تمرين الاستعادة الشهري

على نسخةٍ منفصلة لا تمسّ الإنتاج (اسم مشروع مختلف = قاعدة بيانات ومجلّد أصول
مستقلّان):

```bash
docker compose -p rawda-drill up -d db
# ثم أوامر الاستعادة أعلاه مع `-p rawda-drill` بعد `docker compose`
# النجاح = عدد القصص والأصول يطابق الإنتاج، وقصّة تُفتح بصورها.
docker compose -p rawda-drill down -v      # حذف التمرين كاملاً
```

## حين يتعطّل شيء

| العَرَض | أوّل ما يُفحص |
|---|---|
| صفحة بيضاء | `deploy/smoke.sh` — يسمّي الجزء الفاشل. ثم `--rollback` إن كان بعد نشر |
| «الاستوديو» يفتح تطبيق الويب | عامل خدمة قديم في متصفّح المعلّمة: إعادة تحميل الصفحة مرّة |
| الاستوديو: «لم يُحفظ — انتهت جلسة الدخول» | الرمز صالح ٨ ساعات. فتح الاستوديو من زرّه داخل التطبيق من جديد، **ثم الحفظ من التبويب القديم** (التعديلات فيه) |
| رفع صورة: «ليس من الصيغ المسموحة» | مقصود: الصور png/jpg/webp/gif/avif، والصوت mp3/wav/ogg/m4a/aac/webm/opus/flac |
| «طلبات كثيرة» عند الدخول | ١٠ محاولات/دقيقة لكل عنوان. الانتظار دقيقة |
| صورة لا تظهر في قصّة | `docker compose logs backend \| grep "Not Found"` يسمّي الملف المفقود |
| `/healthz` يقول `"media": false` | مجلّد الأصول لا يُكتب فيه (امتلاء القرص؟): `df -h` |
| `/healthz` يقول `"database": false` | `docker compose ps db` و`docker compose logs db` |
| القرص يمتلئ | `du -sh backups/*` — أرشيفات الأصول اليومية أكبر ما ينمو |

---

## نقل المحتوى إلى الخادم

القصص **لا** تنتقل مع git: بنيتها في قاعدة البيانات وصورها في `media`، والاثنان
ينتقلان معاً أو لا ينتقلان. نقل أحدهما دون الآخر يعطي قصصاً بصورٍ فارغة، بلا
أي رسالة خطأ.
